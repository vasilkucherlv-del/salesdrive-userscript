Userscript для SalesDrive CRM (komplektom.salesdrive.me). Два файли:
- `salesdrive.dev.user.js` — ТЕСТ-версія (шапка «(ТЕСТ)», URL на dev-файл)
- `salesdrive.user.js` — ОСНОВНА (стабільна)

## ГОЛОВНЕ ПРАВИЛО: перед видачею КОЖНОЇ версії — протестуй її сам на живій СРМ

Вимога Василя (01.08.2026): жодна версія не пушиться без самостійного живого тесту.

Порядок тесту через e2e-харнес (`e2e/bridge.js` + сесія `e2e/sd-session.json`):
1. Вхід уже налаштовано; якщо сесія протухла — `SD_LOGIN=... SD_PASS=... NODE_PATH=$(npm root -g) node e2e/login.js`
   (креденшали тех-акаунта дає Василь; НЕ комітити).
2. Димовий тест усіх модулів: `NODE_PATH=$(npm root -g) node e2e/smoke.js` — «ПОМИЛОК НЕМАЄ».
3. Функціональний тест САМЕ зміненої фічі: написати одноразовий скрипт у scratchpad
   (зразки: bundle-live-test.js, round-*.js, preview-*.js в історії сесій) —
   відкрити реальну сторінку, інжектнути dev-скрипт, наклацати фічу, звірити результат.
4. НІЧОГО НЕ ЗБЕРІГАТИ у СРМ без потреби: кліки в одноразовій сесії браузера безпечні,
   поки не натиснуто «Зберегти» / реальний друк / реальний PUT. Записи (PUT тощо) —
   тільки зворотні тести (змінив → перевірив → повернув) або з дозволу Василя.
5. Якщо щось фізично неможливо протестувати (реальний друк, права акаунта) — чесно
   написати це Василю ДО того, як він почне тестувати.

### Обовʼязково, окрім «фіча спрацювала»
Ці дві перевірки додано після того, як Василь сам знайшов миготіння і брак позначок
(01.08.2026) — статичний аудит коду їх НЕ показує:
6. **Тест спокою (миготіння).** Для будь-якого модуля, що малює щось у сторінку на
   пульс `lkdom`: відкрити сторінку, нічого не чіпати 6 с і порахувати мутації наших
   елементів (MutationObserver по `[class^=lk|sd-]`, зразок: scratchpad/churn-sweep.js).
   Норма — **0**. Причина ненуля майже завжди одна: рендер без перевірки «чи змінились
   дані» → лікується підписом стану (`data-sig`) або порівнянням тексту перед записом.
   Прогнати по всіх типах сторінок: список заявок, картка заявки, прихідна накладна,
   каталог товарів, сторінка товару.
   **З ДАНИМИ, а не на порожньому місці**: засіяти стан (запис у localStorage
   `lk_chatfail_v1`, активний перегляд опт-цін тощо) — без даних елемента на сторінці
   немає і миготіння не видно. Саме через це двічі пропустив баг (2.55/2.56).
   Окрема пастка: НЕ шукати ідентифікатори скануванням тексту сторінки
   (`body.innerText`) — можна зловити текст ВЛАСНОЇ плашки і отримати цикл
   показав→сховав. Ідентифікатор брати з `location.hash`/`title`/заголовка.
   **Пастка самого харнеса (11.08.2026):** сторінки СРМ відрізняються лише хешем,
   тож `page.goto('…index.html?formId=1#/…')` НЕ перезавантажує документ, і кожен
   наступний `addScriptTag` додає ЩЕ ОДНУ копію скрипта. Копії з різними кешами
   перемальовують одне за одним → сотні «мутацій», яких у житті немає.
   У обході щоразу міняти query (`&_t=Date.now()`), щоб було справжнє
   перезавантаження. Перш ніж «лікувати» миготіння — перевірити, чи воно є при
   ОДНІЙ інжекції.
7. **Тест покриття.** Якщо фіча привʼязана до сутності (товар, заявка), виписати ВСІ
   місця, де ця сутність зʼявляється, і перевірити КОЖНЕ, а не лише те, де робив.
   Для товару це: рядок у заявці, картка-модалка, каталог `#/product/index`,
   сторінка `#/product/update/ID`, рядки документів (прихідні накладні тощо).
8. **Банер допродажу — окремим тестом ЩОРАЗУ.** Димовий тест його НЕ ловить
   (`upsell:false`): карта допродажу приходить із Google-таблиці, у харнесі це 403.
   Треба засіяти кеш і подивитись на бейджі в часі (зразок: scratchpad/stock-loop.js):
   `localStorage['lkgm_sd_upsell_cache_v1'] = JSON.stringify(JSON.stringify({ts:Date.now(),pairs:[{a:'<назва товару із заявки>',sku:'097',c:'…',s:'…'}]}))`
   перед інжектом, далі відкрити заявку з тим товаром і кожні 5 с читати `.sd-stock`:
   за ~5 с має бути «✓ В наявності: N шт», а не «перевіряю залишок…».
   Причина правила (14.08.2026, 2.80): масова заміна тексту в файлі підмінила
   виклик `requestStock(slots)` У ЯДРІ (перше входження!) — банер назавжди лишився
   в стані «перевіряю залишок…», а всі решта тестів були зелені.
   Звідси ж загальне: **не робити sed/replace по короткому рядку** — однакові
   виклики трапляються в кількох модулях; правити за номером рядка або з якорем.

## Процес релізу
- Правки СПОЧАТКУ в `salesdrive.dev.user.js`, версія +0.01, коміт «ТЕСТ X.XX: …».
- Після «працює» від Василя — перенести в основну:
  `sed 's/ (ТЕСТ)//; s/salesdrive\.dev\.user\.js/salesdrive.user.js/g' dev > stable`,
  звірити diff 0 поза шапкою, коміт «СТАБІЛЬНА X.XX: …».
- Пуш у `main` (реліз-лайн живе там): `git push origin HEAD:main` (fast-forward!).
- Гейти перед комітом: `node --check` обох файлів; рамки модулів START==END
  (`grep -c 'МОДУЛЬ-START'`); усі `DEBUG=false`.

## Архітектура (коротко)
- Кожен модуль у рамці `/* ▼▼▼ МОДУЛЬ-START • name ▼▼▼ */ … МОДУЛЬ-END` + try/catch.
- Ядро (page-context) ↔ модулі (sandbox): міст через атрибути `data-sd-*` на `<html>`
  + CustomEvent (зразки: sdUpsellAdd, sdArrivalOpt, sdRoundPickup).
- Запис у СРМ — тими самими внутрішніми запитами, що робить сама СРМ
  (PUT /products/{id}/ тощо), CSRF — через Angular `CsrfService` (injector).
- API-ключ для читання заявок — у модулях (Form-Api-Key), товари публічним API недоступні.

## ⚠ Ліміт публічного API — 100 запитів НА ГОДИНУ на весь акаунт
Перевищення → HTTP 400 з тілом
`{"status":"error","message":"API limit reached. API method: \"/api/order/list/\". API period: 1 hour. API limit: 100."}`
Ліміт СПІЛЬНИЙ: усі менеджери, усі вкладки, усі модулі — з одного відра.
Правила (після інциденту 10.08.2026 «API постійно зайняте»):
0. **Публічний API — останній засіб.** Той самий список заявок СРМ віддає своїм
   внутрішнім запитом (cookie, без ключа, без ліміту):
   `/orders/?formId=1&mobileMode=0&mode=orderList&page=N&filter[statusId][]=…`
   (є `filter[paymentDate][from]/[to]`, пагінація `pagination.pageCount`, а в рядках —
   `payment_method`, `paymentAmount`/`restPay`, `document_ord_check`, `contacts`,
   `ord_delivery_data` з `isPrinted`, `meta.fields.statusId.options`).
   Єдине, чого там НЕМАЄ, — `sku` товарів (лише `productId`); код товару → productId
   перекладається внутрішнім `/products/data/?active=1&filter[sku]=КОД&formId=1`
   (один код може мати кілька товарів: 069 = і товар, і комплект).
   Обгортка — `window.sdApi.orders(qs, page)`.
1. **Спершу шукай дані на сторінці.** Майже все вже є в Angular-скоупах
   (напр. ТТН і прапорець друку Укрпошти — `viewModel.ukrposhta.barcode/.isPrinted`).
   Запит до API на КОЖНУ відкриту заявку — гарантований злив квоти.
2. **Ніяких повторів «через хвилину».** Вікно ліміту — година; ретрай раз на 65 с
   тримає квоту вичерпаною вічно (саме це й було). На відмову — стоп і чесне
   повідомлення менеджеру.
3. Усі запити до `/api/*` — тільки через `window.sdApi.fetch(url, opts)`
   (модуль `lkApiBudget`): лічильник за годину, спільний стоп-кран на 10 хв,
   резерв 15 запитів для ручних дій (`opts.bg=true` — фонове, у резерв не лізе).
4. Кеші результатів — у `localStorage` (спільні для вкладок), а не в памʼяті модуля.
5. Перед видачею версії: полічити запити до `/api/` за час звичайного відкриття
   заявки (`page.on('request')`) — має бути **0**.

## Застереження з досвіду
- Накладні бувають у €/$: собівартість = ціна × `vm.item.currencyRate` (гривня → 1).
- Поле доставки на картці: `[attr-field-name="shipping_method"]` (не вгадувати id).
- Зміни vm без збереження живуть до перезавантаження сторінки — цим і тестуємо.
- Стоп-хук «Unverified commits» = відсутність GPG-підпису; email уже правильний,
  історію НЕ переписувати.
